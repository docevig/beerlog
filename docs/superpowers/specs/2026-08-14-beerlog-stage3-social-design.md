# beerlog, этап 3 — друзья и общие вечеринки

Дата: 2026-08-14
Статус: архитектура согласована, к реализации не приступали

## 1. Что делаем

Две отдельные сущности поверх личного дневника:

- **Друзья** — постоянные связи. Видно, сколько друг выпил за период, сколько стилей
  попробовал, каков его диапазон по шкале SRM. Сама история отметок не передаётся.
- **Вечеринки** — совместные сессии. Пока сессия идёт, отметки участников видны всем
  за столом: общий счёт, кто что взял, лидерборд вечера.

## 2. Принятые решения

| Развилка | Решение | Почему |
|---|---|---|
| Модель | друзья и вечеринки одновременно | покрывает оба исходных сценария: сравнение и совместный вечер |
| Что уходит на сервер | итоги за период + отметки во время активной вечеринки | личный дневник остаётся личным; общим становится то, что и так происходит на людях |
| Приглашение в друзья | одноразовая ссылка, сгорает через 24 часа | без экрана подтверждения, но утечка ссылки в чужой чат не открывает доступ к статистике |
| Старт вечеринки | ссылка в чат и выбор из списка друзей | ссылка работает с теми, кто ещё не добавлен; список — быстрый путь для своих |

## 3. Хранение данных

**Личная история остаётся в Telegram CloudStorage.** Сервер не становится источником
правды для дневника: он хранит только то, что нужно другим.

На сервере лежит:

- профиль: telegram id, имя, аватар;
- витрина итогов: объём, число порций, стилей, средний SRM за месяц — пересчитывается
  клиентом и отправляется при изменениях;
- связи дружбы;
- вечеринки и отметки внутри них.

Такое разделение означает, что потеря доступа к CloudStorage по-прежнему теряет
подробную историю. Импорт из выгруженного JSON закрывает этот риск и должен появиться
раньше третьего этапа.

## 4. Инфраструктура

**Cloudflare Workers + D1.** Бесплатный тариф: 100 тыс. запросов в день, база 5 ГБ,
5 млн чтений строк и 100 тыс. записей в сутки. Для компании друзей это потолок,
до которого не дотянуться.

Токен бота хранится как секрет Worker и не покидает сервер.

### Схема D1

```sql
CREATE TABLE users (
  tg_id      INTEGER PRIMARY KEY,
  name       TEXT NOT NULL,
  photo_url  TEXT,
  created_at INTEGER NOT NULL
);

-- Витрина итогов: то, что видят друзья
CREATE TABLE totals (
  tg_id     INTEGER NOT NULL,
  period    TEXT NOT NULL,          -- YYYY-MM
  ml        INTEGER NOT NULL,
  portions  INTEGER NOT NULL,
  styles    INTEGER NOT NULL,
  avg_srm   REAL NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (tg_id, period)
);

-- Дружба хранится один раз, порядок пары нормализован
CREATE TABLE friendships (
  low_id   INTEGER NOT NULL,
  high_id  INTEGER NOT NULL,
  since    INTEGER NOT NULL,
  PRIMARY KEY (low_id, high_id),
  CHECK (low_id < high_id)
);

-- Одноразовые приглашения
CREATE TABLE invites (
  code       TEXT PRIMARY KEY,
  kind       TEXT NOT NULL,          -- friend | party
  author_id  INTEGER NOT NULL,
  party_id   TEXT,
  expires_at INTEGER NOT NULL,
  used_by    INTEGER,
  used_at    INTEGER
);

CREATE TABLE parties (
  id         TEXT PRIMARY KEY,
  title      TEXT,
  host_id    INTEGER NOT NULL,
  started_at INTEGER NOT NULL,
  ended_at   INTEGER
);

CREATE TABLE party_members (
  party_id  TEXT NOT NULL,
  tg_id     INTEGER NOT NULL,
  joined_at INTEGER NOT NULL,
  PRIMARY KEY (party_id, tg_id)
);

-- Отметки видны остальным только пока вечеринка не закрыта
CREATE TABLE party_entries (
  id       TEXT PRIMARY KEY,
  party_id TEXT NOT NULL,
  tg_id    INTEGER NOT NULL,
  ts       INTEGER NOT NULL,
  ml       INTEGER NOT NULL,
  style    TEXT NOT NULL,
  name     TEXT
);
```

## 5. Авторизация

Каждый запрос несёт заголовок с `initData`. Worker обязан:

1. Сверить подпись HMAC-SHA-256: секрет — HMAC от токена бота с ключом `WebAppData`.
2. Отклонить `auth_date` старше суток — защита от повторного проигрывания.
3. Брать `tg_id` **из проверенной `initData`**, никогда из тела запроса.

Без этого любой может назваться кем угодно. Пока данных на сервере нет, проверка
не нужна; с появлением общих данных она становится обязательной.

## 6. Приглашения

Ссылка вида `t.me/beerlogs_bot/app?startapp=КОД`. Код приходит в `start_param`
(разрешены латиница, цифры, `_`, `-`, до 512 символов).

Поток:

1. Клиент просит у сервера код: `POST /invites {kind}`.
2. Сервер пишет строку в `invites` со сроком 24 часа и отдаёт код.
3. Пользователь делится ссылкой через `t.me/share/url`.
4. Приглашённый открывает приложение, клиент видит `start_param` и шлёт
   `POST /invites/КОД/accept` вместе с `initData`.
5. Сервер проверяет: код существует, не просрочен, не использован, автор не сам
   приглашённый. Ставит `used_by`, создаёт дружбу либо членство в вечеринке.

Код одноразовый: повторное открытие той же ссылки возвращает «приглашение уже
использовано». Для новых друзей генерируется новый код.

## 7. Методы API

| Метод | Назначение |
|---|---|
| `POST /sync/totals` | отправить свою витрину итогов за период |
| `GET /friends` | список друзей с их итогами за выбранный месяц |
| `DELETE /friends/:id` | удалить дружбу (с обеих сторон) |
| `POST /invites` | создать одноразовый код (`friend` или `party`) |
| `POST /invites/:code/accept` | принять приглашение |
| `POST /parties` | начать вечеринку |
| `POST /parties/:id/invite` | позвать выбранных друзей (уведомление ботом) |
| `POST /parties/:id/entries` | добавить отметку в активную вечеринку |
| `GET /parties/:id` | состояние стола: участники, отметки, счёт |
| `POST /parties/:id/close` | закрыть вечер |

## 8. Как это выглядит в приложении

- Четвёртая вкладка «компания»: список друзей с их месячными итогами, кнопка
  «пригласить», активная или прошедшие вечеринки.
- Во время активной вечеринки экран отметки показывает, что это общий вечер: каждая
  запись уходит и в личный дневник, и на стол.
- Закрытая вечеринка остаётся в истории карточкой: участники, общий объём, кто сколько.

## 9. Что нужно сделать до этапа 3

1. **Импорт из JSON.** Выгрузка есть, восстановления нет — до появления сервера это
   единственный путь вернуть историю.
2. **Полная правка отметки.** Сейчас меняется только объём.
3. **Шаринг текстом.** Готовит почву: ссылка на приложение уже начнёт расходиться.

## 10. Риски

| Риск | Реакция |
|---|---|
| Утечка ссылки-приглашения | код одноразовый и живёт сутки |
| Подделка личности | `tg_id` берётся только из проверенной `initData` |
| Расхождение итогов и дневника | витрина пересчитывается клиентом и перезаписывается целиком, а не правится по частям |
| Заброшенные вечеринки висят активными | автозакрытие через 12 часов после последней отметки |
| Исчерпание бесплатного тарифа D1 | лимит записей 100 тыс./сутки; при компании в десятки человек недостижим |
